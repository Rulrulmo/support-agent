# support-agent 계획

> 2026-10-07 · 개인 포트폴리오 프로젝트

## 1. 무엇을 만드나
제품 문서를 근거로 고객 문의에 답하고, 못 하면 사람에게 넘기는 **AI 상담원**.
- 지식을 **두 층**으로 둔다: 원본 문서를 그대로 검색하는 **RAG**와, LLM이 원본을 정리해 사람이 검수한 **LLM Wiki**
- 모든 개선을 **평가셋으로 측정**하고, 효과가 없으면 버린 기록까지 남긴다
- 데모 대상 제품: **Apache Guacamole** (브라우저로 RDP·VNC·SSH에 접속하는 오픈소스 원격 접속 게이트웨이)

| 항목 | 내용 |

| 라이선스 | Apache License 2.0 — 출처 표시(NOTICE) 후 사용·가공 가능 |

| 언어 | 원본은 영어, 질문은 **한국어 위주**(+ 영어 일부). 위키 페이지는 한국어로 만든다 |

## 3. 구조
```
 원본 (Guacamole 매뉴얼 1.6.0)
   │ 수집: 절 단위 청크 + 임베딩
   ├────────────────────────────┐
   ▼                            ▼
 [RAG] 하이브리드 검색        [LLM Wiki] 컴파일 → 인용 검증 → 검수 → 게시
  (키워드 + 벡터)              (문제해결·주제·참조 페이지, 한국어, 문장마다 원본 인용)
   │                            │  린트: 원본이 바뀌면 stale, 모순·중복·고아 페이지
   └──────────┬─────────────────┘
              ▼
        답변 턴 (위키 먼저 → 부족하면 원본) · 툴 루프 · 출처 표시 · 상담원 이관
              │
        채팅 위젯 · 상담원 콘솔(이관·위키 검수) · 평가 하네스(judge)
```

### 기술
- Java 21 · Spring Boot 4 · Spring Modulith (모듈 경계 테스트) · Spring AI (OpenAI 호환 → LiteLLM)
- PostgreSQL 17 + pgvector (벡터) + 내장 전문 검색(영어 키워드) · Flyway
- LiteLLM: 모델은 용도 이름(answer·judge·wiki·embed)으로만 부르고, 벤더 키는 게이트웨이에만
- React + Vite (위젯·콘솔) · Testcontainers · docker/podman compose

## 4. LLM Wiki
[Karpathy의 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) (2026-04) 방식: 원본은 그대로 두고, **LLM이 정리한 위키를 계속 유지**하며 질문에는 위키를 먼저 본다.
세 층 — **원본**(읽기만, 고치지 않음) · **위키**(LLM이 쓰고 유지) · **스키마**(위키를 어떻게 쓰고 유지할지 정한 규칙 = 이 프로젝트의 지시문 파일).
제품 상담에 맞게 고친 점:

| 원형 | 이 프로젝트 |
|---|---|
| 파일에 쓴 마크다운 | DB에 저장 (상태·버전·출처 관계를 질의할 수 있게) |
| LLM이 쓰면 바로 반영 | **draft → 검수 → published**. 답변에는 published만 쓴다 (오류 누적 방지) |
| 출처는 선택 | **문장마다 원본 청크 인용**, 인용이 원본에 실제로 있는지 코드가 검사 |
| 언어 제약 없음 | 영어 원본 → **한국어 페이지** (한국어 질문의 검색·답변 품질) |

### 페이지 종류
| 종류 | 내용 | 예 |
|---|---|---|
| troubleshooting | 증상 → 원인 → 확인 → 해결 | "로그인은 되는데 연결 화면이 검은색" |
| topic | 기능·설정 개요와 관련 페이지 링크 | "LDAP 인증" |
| reference | 설정 키·파라미터 표 | "guacamole.properties 주요 키" |
| index | 전체 목차: 종류별 페이지와 한 줄 요약 (질의 때 먼저 읽는다) | |
- **log**: 컴파일·검수·린트·질의 기록을 시간순으로만 쌓는다 (위키가 어떻게 바뀌어 왔는지)

### 동작
- **컴파일**: 원본 → 페이지 계획(목록) → 페이지 작성 → 인용 검증 → draft
- **검수**: 콘솔에서 승인·반려 (반려 사유는 다시 컴파일할 때 반영)
- **질의**: 답변 턴이 index → 관련 페이지를 먼저 보고, 부족하면 원본 검색
- **린트**: 원본 버전이 바뀌면 인용 청크가 바뀐 페이지를 stale로, 페이지 간 모순·중복·고아 페이지를 검수 대기열에
- (나중) **되돌려 쓰기**: 좋은 답변·상담원이 해결한 이관 건 → 페이지 후보 (원형의 "좋은 답은 위키에 다시 쓴다")

## 5. 평가
- 평가셋: 매뉴얼을 읽고 **직접 쓴** 질문 (한국어 위주), 기대 요점·금지 사항·근거 절·기대 동작(답변·되묻기·이관)
- 같은 질문을 **RAG만 / 위키만 / 위키 + RAG**로 돌려 정답률·환각률·지연·비용을 비교 (judge는 답변과 다른 벤더 모델)
- 개선마다 같은 평가로 확인하고, 효과가 없으면 되돌린 기록을 남긴다
